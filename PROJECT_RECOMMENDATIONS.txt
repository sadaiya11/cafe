======================================================================
2. GO-LIVE BLOCKERS
======================================================================

These items should be fixed before making the application publicly available.

2.1 ADMIN AUTHENTICATION IS NOT SECURE

The admin session is stored in browser localStorage, and API requests do not properly verify authentication or roles.

The admin login also contains hardcoded demo credentials and PINs in:

src/components/AdminAuthGuard.jsx

Potential impact:

- Anyone can call admin APIs directly
- Products can be changed or deleted
- Order statuses can be changed
- Customer records can be read
- Store settings and banners can be modified
- Images can be uploaded

Required solution:

- Implement server-side sessions or signed JWT authentication
- Add role-based access control
- Protect every admin API route on the server
- Add session expiration and logout invalidation
- Remove demo PINs and fallback credentials from production

2.2 PASSWORDS ARE STORED AS PLAIN TEXT

Passwords are saved and compared directly in:

backend/server.js

Required solution:

- Use Argon2id or bcrypt password hashing
- Never return password fields in API responses
- Invalidate existing sessions after migration
- Force existing users to reset passwords if necessary
- Enforce a stronger password policy

2.3 ORDER PRICES ARE CONTROLLED BY THE BROWSER

The frontend sends product prices, totals, items, discounts and payment amounts to the backend.

A malicious customer could modify the request and pay less than the actual product price.

The browser should send only:

- Product ID
- Variant ID
- Quantity
- Coupon code
- Delivery address

The server must recalculate:

- Product and variant prices
- Product availability
- Quantity limits
- Tax
- Delivery fee
- Coupon discount
- Final payable amount

2.4 CUSTOMER DATA APIs ARE EXPOSED

Customer orders and admin customer records are available through API routes without adequate ownership and role verification.

Required rules:

- A customer can only view their own orders
- An admin can view all orders only after server-side authorization
- Customer search must require an authenticated admin role
- Never use a customer-supplied email address as proof of identity

2.5 PAYMENT VERIFICATION IS INCOMPLETE

Payment signature verification alone is not sufficient.

The server should also:

- Verify the Razorpay order amount
- Verify payment status directly with Razorpay
- Store the gateway order ID and payment ID
- Reject duplicate payment processing
- Process Razorpay webhooks
- Handle failed payments
- Handle refunds
- Match payment amount with the server-calculated order total

2.6 BUSINESS DATA IS STORED IN LOCALSTORAGE

Coupons, reviews, inventory, settings, order fallbacks and order status overrides use browser localStorage in different parts of the application.

This causes data loss or inconsistency when:

- Browser storage is cleared
- Another admin uses another computer
- Multiple staff members work at the same time
- The application is opened on another device
- A user edits local data manually

These features must be stored in the database before launch.

2.7 TWO BACKENDS CAN BEHAVE DIFFERENTLY

There are two backend implementations:

- backend/server.js
- api/index.js

They have different payment behavior, persistence behavior and fallback logic.

This can cause local development to work while the deployed Vercel version fails.

Recommended solution:

- Use one authoritative backend
- Or move shared business logic into common modules
- Test the local and production API behavior with the same integration tests

2.8 TAX AND STORE SETTINGS ARE INCONSISTENT

The admin can configure tax, but the cart currently calculates tax as zero.

Store closed status and delivery rules are mainly checked in the frontend. These rules must also be enforced on the server.

2.9 HARDcoded FALLBACK SECRETS EXIST

The backend contains fallback admin and email credentials.

Required solution:

- Remove all fallback passwords and API keys
- Rotate any credentials that may have been exposed
- Store secrets only in deployment secret storage
- Add secret scanning to CI
- Never commit .env files

2.10 FILE UPLOADS NEED VALIDATION

Image uploads should not trust only the declared MIME type.

Add:

- File signature validation
- Maximum dimensions
- Maximum file size
- Image re-encoding
- Authenticated upload endpoints
- Storage cleanup for replaced images

2.11 LINT AND DEPENDENCY ISSUES

The frontend production build succeeds, but npm run lint currently fails because the ESLint configuration references an unavailable React Hooks plugin export.

The backend dependency audit reports two moderate qs vulnerabilities through Express.

Fix these before setting up CI/CD.

2.12 MISSING TEST COVERAGE

There are no meaningful automated tests for the critical business paths.

At minimum, add tests for:

- Authentication
- Admin authorization
- Password hashing
- Order ownership
- Price calculation
- Coupon validation
- Payment verification
- Duplicate payment handling
- Store closure rules
- Inventory deduction

======================================================================
6. DATA SECURITY AND OPERATIONS
======================================================================

Implement:

- HTTPS everywhere
- Restricted CORS origins
- Rate limiting on login, password reset and payment routes
- Request validation using a schema library
- Secure HTTP headers
- Secure cookies if using sessions
- CSRF protection where applicable
- Database backups
- Database restore testing
- Error monitoring
- Uptime monitoring
- Payment failure alerts
- Admin login alerts
- Production logging without passwords or payment secrets
- Separate development, staging and production environments

Never store:

- Plain text passwords
- Razorpay secret keys in frontend code
- Full payment card details
- Unnecessary identity documents
- Secrets inside source code

======================================================================
8. FINAL GO-LIVE DECISION
======================================================================

The frontend production build currently succeeds, but the system should not be deployed publicly until these are fixed:

- Authentication and authorization
- Plain text password storage
- Client-controlled order pricing
- Payment verification
- Customer data exposure
- LocalStorage business data
- Hardcoded credentials
- Backend implementation differences
- Missing tests and monitoring

After those items are resolved, the project will have a much safer foundation for customer ordering, staff operations and future business reporting.
